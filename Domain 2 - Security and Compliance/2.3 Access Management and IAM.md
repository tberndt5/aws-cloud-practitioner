# 2.3 Identify AWS access management capabilities

> [!abstract] Exam guide objective (verbatim from the CLF-C02 exam guide)
> **Knowledge of:**
> - Identity and access management (for example, AWS Identity and Access Management [IAM])
> - Importance of protecting the AWS root user account
> - Principle of least privilege
> - AWS IAM Identity Center (AWS Single Sign-On)
>
> **Skills in:**
> - Understanding access keys, password policies, and credential storage (for example, AWS Secrets Manager, AWS Systems Manager)
> - Identifying authentication methods in AWS (for example, multi-factor authentication [MFA], IAM Identity Center, cross-account IAM roles)
> - Defining groups, users, custom policies, and managed policies in compliance with the principle of least privilege
> - Identifying tasks that only the account root user can perform
> - Understanding which methods can achieve root user protection
> - Understanding the types of identity management (for example, federated)

## Big picture

Access management decides **who** can sign in (authentication) and **what** they can do (authorization). On AWS that is mainly AWS Identity and Access Management (IAM): users, groups, roles, and the JSON policies attached to them, all granted by the principle of least privilege. The exam checks that you know how to protect the root user, which tasks only the root user can do, the difference between a user and a role, the three kinds of policies, when to use IAM Identity Center or federation instead of IAM users, and where to store credentials (Secrets Manager vs Systems Manager Parameter Store). Questions are mostly "what is the best practice" or "which feature does this".

## Key concepts

### Authentication vs authorization

- **Authentication:** proving who you are (password, access keys, MFA, federated sign-in).
- **Authorization:** deciding what an authenticated identity may do (IAM policies). By default everything is **denied**; an explicit **Allow** grants access; an explicit **Deny** always overrides any Allow.

IAM is a global service (not tied to a Region) and is offered at no additional charge.

### IAM identities

| Identity | What it is | Credentials | Use it for |
| --- | --- | --- | --- |
| **Root user** | The identity created with the account (email address and password); unrestricted access to everything | Email + password, optional access keys (not recommended) | Only the few tasks that require it |
| **IAM user** | A person or application inside one account | Long-term: console password and/or access keys | Specific cases needing long-term credentials; AWS now recommends federation through IAM Identity Center for people |
| **IAM group** | A collection of IAM users; attach policies once and every member gets them | None (a group cannot sign in and is not a principal in a policy) | Managing permissions by job function (Admins, Developers) |
| **IAM role** | An identity with permissions that is **assumed** by a trusted entity | **Temporary** credentials issued by AWS STS (Security Token Service) | EC2 instances and Lambda functions calling AWS services, cross-account access, federated users |

Key facts:
- Groups contain users only; groups cannot contain other groups. A user can be in several groups.
- A role has no password or access keys of its own. Whoever assumes it gets short-lived credentials that expire automatically.
- ==For an application on EC2, attach an IAM role to the instance; never store access keys on the instance.==

### IAM policies

A **policy** is a JSON document with statements of Effect (Allow or Deny), Action (for example `s3:GetObject`), and Resource (an ARN, Amazon Resource Name), with optional Conditions.

| Policy type | Who creates it | Reusable | Notes |
| --- | --- | --- | --- |
| **AWS managed policy** | AWS | Yes, attach to many identities | Updated by AWS; often broad (for example AdministratorAccess, ReadOnlyAccess); job-function policies exist |
| **Customer managed policy** | You | Yes, attach to many identities in your account | You control the exact permissions; the best way to write least-privilege "custom policies" |
| **Inline policy** | You | No: embedded in one user, group, or role | Deleted with the identity; use only for a strict one-to-one relationship |

Other policy types worth recognizing:
- **Identity-based policies** attach to users, groups, and roles. **Resource-based policies** attach to a resource, such as an S3 bucket policy or an SQS queue policy, and name the principals that may access it.
- **Service control policies (SCPs)** in AWS Organizations set the maximum permissions for accounts in an organization; they grant nothing by themselves.
- **Permissions boundaries** set the maximum permissions an IAM entity can have.

### Principle of least privilege

Grant only the permissions required to do a task, and nothing more. In practice:
- Put users in groups by job function and attach policies to groups, not individual users.
- Prefer customer managed policies scoped to specific actions and resources over broad AWS managed policies.
- Use roles and temporary credentials instead of long-term keys.
- Review and remove unused permissions with **IAM access advisor / last accessed information** and **IAM Access Analyzer** (which can also generate a least-privilege policy from CloudTrail activity).

### Root user protection

The root user can do anything and its permissions cannot be limited by IAM policies in its own account (SCPs from AWS Organizations can restrict a member account's root user). Methods to protect it:

1. ==Enable **MFA** on the root user.==
2. **Do not create root access keys**; delete any that exist.
3. Use a strong, unique password; keep the root email address secure (a distribution list the company controls is common).
4. Create an administrative identity (in IAM Identity Center, or an IAM user) for daily work, and **do not use the root user for everyday tasks**, including administrative ones.
5. Monitor root sign-ins (CloudTrail, and alerts via Amazon EventBridge).
6. Store root credentials securely and limit who knows them.

Current status: the IAM User Guide states that MFA is now enforced for root users by default, and AWS Organizations can centrally remove root user credentials from member accounts.

### Tasks only the root user can perform

From the IAM User Guide ("Tasks that require root user credentials"):

- **Change account settings:** the root user email address, root user password, and root user access keys. (Account name, contact information, and alternate contacts no longer require root.)
- **Close the AWS account** (and reopen it during the post-closure period).
- **Restore IAM user permissions** when the only IAM administrator accidentally revoked their own permissions.
- **Activate IAM access to the Billing and Cost Management console.**
- **View certain tax invoices.**
- **Sign up for AWS GovCloud (US)** and request GovCloud root access keys from AWS Support.
- **Register as a seller in the EC2 Reserved Instance Marketplace.**
- **Configure an S3 bucket to enable MFA Delete.**
- **Edit or delete an S3 bucket policy that denies all principals.**
- **Edit or delete an SQS queue policy that denies all principals.**

Older study materials also list "change or cancel your AWS Support plan" as a root-only task. Current status: the current IAM User Guide list no longer includes it; if an exam option offers it alongside clearer root tasks such as closing the account, pick the clearer one.

Mnemonic: **Close, Change root email/password, Billing access, Restore admin, Tax, GovCloud, RI seller, MFA Delete, Locked-out bucket or queue policy.**

### Authentication methods

- **Passwords** for console sign-in, governed by an **IAM password policy**: minimum length, required character types, expiration (maximum age), preventing reuse, and whether users can change their own password. The password policy applies to IAM users, not the root user. "Set password policies" is a customer responsibility.
- **Access keys** for programmatic access (CLI, SDKs, APIs): an access key ID plus a secret access key. Long-term credentials: never share or embed in code, rotate regularly, delete unused ones, and prefer roles.
- **Multi-factor authentication (MFA):** something you know (password) plus something you have. Supported types: virtual authenticator apps, passkeys and FIDO2 security keys, and hardware TOTP tokens. Enable for root and all human users.
- **IAM roles and temporary credentials:** including **cross-account IAM roles**, where a role in account B trusts account A so users in A can assume it and work in B without a second set of long-term credentials.
- **IAM Identity Center (AWS Single Sign-On):** one sign-in portal for workforce users to reach multiple AWS accounts and business applications.
- **Federation:** sign in with an existing external identity (corporate directory or web identity) instead of creating IAM users.

### Types of identity management

| Approach | What it means | AWS service |
| --- | --- | --- |
| IAM users in each account | Identities created and managed directly in IAM | [[Services - Security, Identity, and Compliance#AWS Identity and Access Management (IAM)\|IAM]] |
| **Workforce federation / single sign-on** | Employees use one identity (from Identity Center's own directory, Microsoft Active Directory, or an external identity provider such as Okta or Microsoft Entra ID) to access many AWS accounts and apps | [[Services - Security, Identity, and Compliance#AWS IAM Identity Center (AWS Single Sign-On)\|IAM Identity Center]] (recommended), or IAM SAML 2.0 identity providers |
| **Customer (consumer) identity for apps** | End users of your web or mobile app sign up and sign in, including with social providers (Google, Facebook, Apple, Amazon) or SAML/OIDC | [[Services - Security, Identity, and Compliance#Amazon Cognito\|Amazon Cognito]]: user pools (user directory, sign-up and sign-in) and identity pools (exchange identities for temporary AWS credentials) |
| **Microsoft Active Directory** | Run or connect to AD for Windows workloads and AD-aware apps | [[Services - Security, Identity, and Compliance#AWS Directory Service\|AWS Directory Service]]: AWS Managed Microsoft AD, AD Connector (proxy to on-premises AD), Simple AD |
| **Cross-account access** | Identities in one account act in another | IAM roles; also [[Services - Security, Identity, and Compliance#AWS Resource Access Manager (AWS RAM)\|AWS RAM]] to share resources themselves |

**Federation** in one sentence: AWS trusts an external identity provider (IdP) to authenticate the user, then gives the user temporary credentials through a role. No IAM user is created.

### Credential storage: Secrets Manager vs Parameter Store

| | [[Services - Security, Identity, and Compliance#AWS Secrets Manager\|AWS Secrets Manager]] | [[Services - Management and Governance#AWS Systems Manager\|AWS Systems Manager]] Parameter Store |
| --- | --- | --- |
| Purpose | Store, manage, and **automatically rotate** secrets (database credentials, API keys, OAuth tokens) | Store configuration data and secrets as parameters (plain text or SecureString encrypted with KMS) |
| Rotation | ==Built-in automatic rotation== (native for Amazon RDS, Aurora, Redshift, DocumentDB; Lambda for others) | No built-in rotation |
| Cost | Charged per secret per month plus API calls | Standard parameters at no additional charge; advanced parameters charged |
| Cue | "Rotate database credentials automatically", "remove hard-coded passwords" | "Store configuration values or license keys centrally", "cheapest place for a parameter" |

Both encrypt with AWS KMS and control access with IAM. Never store credentials in source code or in an EC2 user data script.

### Access reports and analysis tools

- **IAM credential report:** an account-level CSV listing every user and the status of their password, access keys (including last used and last rotated), and MFA. Use it to audit credentials.
- **IAM access advisor / last accessed information:** shows the services a user, group, role, or policy has permission to use and when they were last accessed. Use it to remove unused permissions.
- **IAM Access Analyzer:** identifies resources (S3 buckets, IAM roles, KMS keys, and others) shared with an external entity outside your account or organization, finds unused access, validates policies, and can generate policies from activity.

## Exam traps and commonly confused

> [!warning] IAM user vs IAM role
> A user has **long-term** credentials and represents one person or app. A role has **temporary** credentials and is **assumed**. For EC2, Lambda, cross-account, and federated access, the answer is a role.

> [!warning] Group vs role
> A group is just a container of users for attaching policies; it cannot be assumed and cannot sign in. A role is assumed by users, services, or other accounts.

> [!warning] Managed vs inline policy
> Managed policies (AWS or customer) are standalone and reusable. Inline policies are embedded in one identity. "Reusable custom permissions" = customer managed policy.

> [!warning] IAM Identity Center vs Cognito
> Identity Center = your **employees** (workforce) accessing AWS accounts and business apps. Cognito = your **app's customers** signing in to your web or mobile app.

> [!warning] Directory Service vs IAM Identity Center
> Directory Service runs or connects **Microsoft Active Directory**. Identity Center provides **single sign-on** and can use AD (through Directory Service) as its identity source.

> [!warning] Secrets Manager vs Parameter Store
> Both store secrets. Only Secrets Manager has **built-in automatic rotation**. Parameter Store is cheaper (free standard tier) and is for configuration data too.

> [!warning] Root user best practice
> "Use the root user for administrative tasks" is wrong; create an administrative identity and lock root away. "Delete the root user" is impossible for a standalone account; secure it with MFA and no access keys.

> [!warning] Access keys vs key pairs
> Access keys sign API and CLI calls. EC2 key pairs are SSH keys to log in to Linux instances. KMS keys encrypt data. Different things.

> [!warning] IAM credential report vs access advisor vs Access Analyzer
> Credential report = status of every user's credentials. Access advisor / last accessed = which services were used and when. Access Analyzer = which resources are shared outside your zone of trust.

## Quick self-check

> [!question]- What is the best way to give an application on an EC2 instance access to an S3 bucket?
> Attach an IAM role (instance profile) to the instance. Do not store access keys on it.

> [!question]- Name four tasks that only the root user can perform.
> Any four of: change the root email, password, or root access keys; close the account; restore IAM permissions for a locked-out admin; activate IAM access to Billing; view certain tax invoices; sign up for GovCloud; register as an RI Marketplace seller; enable MFA Delete on an S3 bucket; edit an S3 bucket or SQS queue policy that denies all principals.

> [!question]- What are the two most important steps to protect the root user?
> Enable MFA and do not create (or delete) root access keys; then stop using root for daily work.

> [!question]- Which policy type is reusable and fully controlled by the customer?
> Customer managed policy.

> [!question]- Which service gives employees single sign-on to multiple AWS accounts?
> AWS IAM Identity Center (AWS Single Sign-On).

> [!question]- Which service lets users of a mobile app sign in with Google or Facebook?
> Amazon Cognito.

> [!question]- Which service automatically rotates database credentials?
> AWS Secrets Manager.

> [!question]- What does an IAM password policy control, and whom does it apply to?
> Rules such as minimum length, character types, expiration, and reuse prevention, for IAM users (not the root user).

> [!question]- Which tool lists all IAM users with the status of their passwords, access keys, and MFA?
> The IAM credential report.

> [!question]- How can users in account A work in account B without new IAM users in B?
> A cross-account IAM role in account B that trusts account A.
