# 3.4 Identify AWS database services

> [!abstract] Exam guide objective (verbatim from the CLF-C02 exam guide)
> **Knowledge of:**
> - AWS database services
> - Database migration
>
> **Skills in:**
> - Deciding when to use EC2 hosted databases or AWS managed databases
> - Identifying relational databases (for example, Amazon RDS, Amazon Aurora)
> - Identifying NoSQL databases (for example, DynamoDB)
> - Identifying memory-based databases
> - Identifying database migration tools (for example AWS Database Migration Service [AWS DMS], AWS Schema Conversion Tool [AWS SCT])

## Big picture

AWS offers "purpose-built" databases: a different managed service for each data model, instead of one database for everything. The exam asks you to match a data model or workload to its service (relational and SQL to RDS or Aurora, key-value at massive scale to DynamoDB, graph to Neptune, microsecond in-memory access to ElastiCache or MemoryDB, analytics over petabytes to Redshift), to decide when a self-managed database on EC2 makes sense instead of a managed one, and to pick the migration tool (DMS moves the data, SCT converts the schema when the engine changes). Distractors are usually other database names, so one-line recognition of each matters.

## Key concepts

### Databases on EC2 vs AWS managed databases

| | Database on Amazon EC2 (self-managed) | AWS managed database (RDS, Aurora, DynamoDB, ...) |
| --- | --- | --- |
| Who installs and patches the OS and database software | **You** | **AWS** |
| Backups, high availability, scaling | You build and run them | Built in (automated backups, Multi-AZ, read replicas, push-button scaling) |
| Control | Full: any engine, any version, OS access, custom configuration | Limited to supported engines, versions, and settings; no OS access (RDS) |
| Choose it when | You need an engine or version a managed service doesn't support, OS-level access, or a third-party feature or configuration that requires the host | You want to reduce administration and focus on the application (the usual exam answer) |

Under the shared responsibility model, with RDS AWS patches the database OS and engine ("patch OS of RDS instances" is an AWS responsibility); you still manage access, network rules, data, and query tuning. On EC2, "patch OS of EC2 instances" is yours. See [[2.1 Shared Responsibility Model]]. AWS recommends RDS as the default choice for most relational deployments.

### Relational databases: Amazon RDS and Amazon Aurora

A **relational database** stores data in tables with rows and columns, uses a fixed **schema**, supports **SQL** queries and joins, and is used for **OLTP** (online transaction processing): orders, accounts, inventory.

**Amazon RDS** (Relational Database Service): "set up, operate, and scale a relational database in the cloud."

- **Engines:** ==Amazon Aurora, MySQL, PostgreSQL, MariaDB, Oracle, Microsoft SQL Server== (and IBM Db2, added in late 2023). Oracle and SQL Server support bring-your-own-license or license-included options.
- **Multi-AZ deployment:** RDS keeps a **synchronous standby** copy in a different AZ and **fails over automatically** if the primary fails. Purpose: ==high availability and durability==. In the classic Multi-AZ instance deployment the standby does not serve reads.
- **Read replicas:** **asynchronous** copies that serve **read-only** traffic. Purpose: ==scale reads== and offload reporting; can be in another Region for disaster recovery or lower read latency, and can be promoted to a standalone database.
- **Automated backups:** daily snapshots plus transaction logs, kept for a retention period you set (up to 35 days), enabling **point-in-time recovery**. **Manual snapshots** are kept until you delete them.
- Storage on EBS, can scale storage; change instance class to scale compute (vertical scaling).

**Amazon Aurora**: "database engine that is compatible with MySQL and PostgreSQL." AWS-built, cloud-native relational engine, managed through RDS.

- AWS markets it as up to 5x the throughput of standard MySQL and 3x standard PostgreSQL, at a lower cost than commercial databases.
- Storage replicates your data **six ways across three AZs**, heals itself, and grows automatically.
- Up to **15 low-latency read replicas**; continuous backup to S3 and point-in-time recovery.
- Options to recognize: **Aurora Serverless** (capacity scales automatically with demand) and **Aurora Global Database** (one database spanning multiple Regions).

Exam cue: "MySQL or PostgreSQL compatible with higher performance and availability" = Aurora. "Oracle or SQL Server" = RDS (Aurora does not run those engines).

### NoSQL: Amazon DynamoDB

**NoSQL** ("not only SQL") databases use flexible, non-tabular data models and scale horizontally. Types include key-value, document, graph, wide-column, and time series.

**Amazon DynamoDB**: "NoSQL database service with fast and predictable performance and seamless scalability; schemaless."

- **Key-value and document** data model; items in tables, no fixed schema beyond the key.
- **Serverless**: no servers or engine versions to manage; ==single-digit millisecond performance at any scale==.
- Capacity modes: **on-demand** (pay per request, for unpredictable traffic) or **provisioned** (set read/write capacity, can auto scale).
- Data replicated across three AZs automatically. **Global tables** replicate a table across multiple Regions (multi-active).
- **DAX (DynamoDB Accelerator)**: an in-memory cache in front of DynamoDB that cuts reads from milliseconds to **microseconds**, with no application rewrite for caching logic.
- Cues: "serverless NoSQL", "key-value", "millions of requests per second", "gaming leaderboards, shopping carts, session data, IoT", "schemaless".

You control who and what can access the tables (IAM); "determine which services have access to DynamoDB tables" is a customer responsibility in the reference guide.

### In-memory (memory-based) databases

Data lives in RAM, so reads and writes take **microseconds** instead of milliseconds.

| Service | What it is | Durable primary database? | Use it for |
| --- | --- | --- | --- |
| **Amazon ElastiCache** | Managed in-memory **cache**; engines Redis and Memcached | No: a cache in front of another database | Caching frequent queries, session stores, leaderboards; reduce load on RDS |
| **Amazon MemoryDB for Redis** | "Durable, in-memory database service that delivers ultra-fast performance" | **Yes**: data stored durably with a Multi-AZ transaction log | Primary database that needs microsecond reads and Redis compatibility |
| **DAX** | In-memory cache **only for DynamoDB** | No | Microsecond reads from DynamoDB |

Current status: AWS now calls the MemoryDB service "Amazon MemoryDB" (compatible with Valkey and Redis OSS), and Amazon ElastiCache supports Valkey, Memcached, and Redis OSS. The exam uses the older names.

### Graph: Amazon Neptune

**Amazon Neptune**: "graph database service for highly connected datasets." Stores **nodes and relationships**, so queries like "friends of friends" are fast. Cues: ==social networks, recommendation engines, fraud detection, knowledge graphs==, network/IT relationships.

### Data warehouse: Amazon Redshift

**Amazon Redshift**: "petabyte-scale data warehouse with automatically provisioned resources and intelligent scaling." Columnar storage, SQL queries, built for **OLAP** (online analytical processing): complex analytics and business intelligence over large historical data sets, not day-to-day transactions. Redshift is listed under Analytics in the exam guide; see [[3.7 AI-ML and Analytics Services]].

OLTP vs OLAP: many small, fast transactions (RDS, Aurora, DynamoDB) vs large analytical queries across lots of data (Redshift).

### Other purpose-built databases (recognition only, for eliminating distractors)

These are **not** on the CLF-C02 in-scope list, but may appear as wrong options:

| Service | Data model | One-line cue |
| --- | --- | --- |
| Amazon DocumentDB (with MongoDB compatibility) | Document (JSON) | "MongoDB workloads" |
| Amazon Keyspaces (for Apache Cassandra) | Wide-column | "Cassandra workloads" |
| Amazon Timestream | Time series | "IoT sensor readings over time" |
| Amazon QLDB (Quantum Ledger Database) | Ledger (immutable, cryptographically verifiable history) | "immutable transaction log" |

Current status: Amazon QLDB reached end of support on July 31, 2025 (listed in the AWS "Services in Full Shutdown" page).

### Database migration: AWS DMS and AWS SCT

**AWS DMS** (Database Migration Service): "migrate relational databases, data warehouses, NoSQL databases, and data stores to AWS."

- ==The source database stays fully operational during the migration==, which minimizes downtime.
- One-time full load or **continuous replication** of ongoing changes (change data capture) to keep source and target in sync until cutover.
- Also used for ongoing replication, consolidating databases, and moving data into S3 or Redshift.

**AWS SCT** (Schema Conversion Tool): "convert an existing database schema from one database engine to another." A downloadable application that converts tables, views, stored procedures, and functions, and flags what it cannot convert automatically.

| Migration type | Meaning | Tools |
| --- | --- | --- |
| **Homogeneous** | Same engine at source and target (Oracle to RDS for Oracle, MySQL to Aurora MySQL) | **DMS** alone (schema is already compatible; native tools also work) |
| **Heterogeneous** | Different engines (Oracle to Aurora PostgreSQL, SQL Server to MySQL) | **SCT first** to convert schema and code, **then DMS** to move the data |

Current status: AWS DMS now also offers **DMS Schema Conversion** inside the DMS console as an alternative to downloading SCT. The exam guide names AWS SCT.

For moving very large databases offline when bandwidth is limited, AWS Snow Family devices can carry the data ([[Services - Migration and Transfer#AWS Snow Family|AWS Snow Family]]); migration strategy is covered in [[1.3 Migration Strategies and AWS CAF]].

## Exam traps and commonly confused

> [!warning] Multi-AZ vs read replicas
> **Multi-AZ** = high availability (synchronous standby, automatic failover). **Read replicas** = read performance (asynchronous, read-only copies). "Improve availability" vs "improve read performance".

> [!warning] RDS vs Aurora
> Aurora is one of the engines you launch through RDS, but only MySQL- or PostgreSQL-compatible. Oracle or SQL Server always means RDS.

> [!warning] DynamoDB vs RDS
> Fixed schema, SQL joins, complex transactions across tables = RDS/Aurora. Flexible schema, key-value lookups at huge scale, serverless = DynamoDB.

> [!warning] ElastiCache vs MemoryDB vs DAX
> ElastiCache = cache for any database. MemoryDB = **durable primary** in-memory database. DAX = cache **only for DynamoDB**.

> [!warning] Redshift vs RDS
> Redshift = analytics (OLAP, data warehouse). RDS = transactions (OLTP). "Data warehouse" is always Redshift.

> [!warning] DMS vs SCT
> DMS **moves the data**. SCT **converts the schema**. Changing engines (heterogeneous) needs both, SCT first. Same engine (homogeneous) needs only DMS.

> [!warning] DMS vs AWS Application Migration Service
> DMS migrates **databases**. Application Migration Service rehosts (lift and shift) **whole servers**.

> [!warning] Database on EC2
> Only the right answer when the scenario needs OS access, an unsupported engine or version, or full control. Otherwise the managed service wins on operational overhead.

## Quick self-check

> [!question]- A company wants a managed relational database running Microsoft SQL Server. Which service?
> Amazon RDS (RDS for SQL Server).

> [!question]- Which RDS feature provides automatic failover to a standby in another AZ?
> Multi-AZ deployment.

> [!question]- Which RDS feature scales read-heavy workloads?
> Read replicas.

> [!question]- How many copies of data does Aurora keep, and across how many AZs?
> Six copies across three AZs.

> [!question]- Which serverless NoSQL database delivers single-digit millisecond performance at any scale?
> Amazon DynamoDB.

> [!question]- Which option adds microsecond-latency caching specifically to DynamoDB?
> DynamoDB Accelerator (DAX).

> [!question]- Which in-scope service is a durable in-memory database rather than a cache?
> Amazon MemoryDB for Redis.

> [!question]- A fraud detection application needs to query relationships among accounts, devices, and transactions. Which database?
> Amazon Neptune (graph).

> [!question]- Migrating Oracle to Aurora PostgreSQL: which tools, in what order?
> AWS SCT to convert the schema, then AWS DMS to migrate the data.

> [!question]- When would you run a database on EC2 instead of RDS?
> When you need OS-level access or an engine, version, or configuration that the managed service doesn't support.
